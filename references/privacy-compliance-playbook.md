# 隐私合规 Playbook（增量信息）

> 本文是 `skills/privacy-compliance` 的深层手册。只放**决策树 + 命令 + 检查清单 + 踩坑点**，不重复子技能概述。使用前先读「框架适用性决策树」定位要守哪部法。

## 1. 框架适用性决策树

```
你处理个人数据吗？（姓名/邮箱/手机号/位置/设备ID/生物特征…）
│
├─ 否 → 本 playbook 不适用，跳过。
│
└─ 是 → 看「用户/业务」落点：
     │
     ├─ 用户位于欧盟(EU/EEA)，或向 EU 用户提供服务 → GDPR 适用
     ├─ 用户位于加州(California)，且达到营收/数据量门槛 → CCPA/CPRA 适用
     ├─ 处理中国境内用户信息，或向境内提供产品/服务 → PIPL（中国）适用
     └─ 多地用户 → 多框架叠加，取最严共性要求兜底
```

**踩坑点**
- GDPR 的「向 EU 用户提供服服」不看公司所在地，只看**用户是否在 EU**——哪怕你在亚洲，只要服务 EU 居民就触发。
- PIPL 的「敏感个人信息」（生物识别、宗教、医疗、行踪、14 岁以下儿童）门槛更高，需**单独同意**。
- CCPA/CPRA 有营收/数据量门槛（如年营收 >$2500 万或买卖 10 万人以上数据），小产品可能不触发。

## 2. PII 盘点清单（数据映射）

逐字段回答，产出一张表：

| 字段 | 类型(普通/敏感) | 存储位置 | 用途 | 保留期 | 第三方共享 | 跨境? |
|------|----------------|----------|------|--------|-----------|-------|
| 邮箱 | 普通 | DB/表X | 登录通知 | 账号存续期 | 邮件服务商 | 否 |
| 手机号 | 普通/敏感(看场景) | … | 2FA | … | … | … |

**命令（轻量辅助，非子技能脚本）**
```bash
# 快速扫一眼代码/配置里是否硬编码了疑似 PII 字段名
grep -rniE "email|phone|mobile|id_card|passport|birth|address|geo|location" --include=*.py --include=*.ts --include=*.json src/ | head -40
```

**踩坑点**
- 容易漏掉「间接标识符」：设备 ID、IP、Cookie ID 组合后也能定位个人，GDPR 把它们算个人数据。
- 日志里的 PII 最常被忽略（把用户邮箱打进 debug 日志）。

## 3. DPIA（数据保护影响评估）步骤

仅对**高风险处理**需要（大规模敏感数据、系统性画像/评分、监控类、跨境大规模传输）。

1. 描述处理活动与目的。
2. 评估必要性与相称性（是否过度收集？）。
3. 识别对数据主体的风险（泄露、歧视、无法更正）。
4. 评估现有缓解措施。
5. 剩余风险是否高 → 高则需先咨询监管机构（GDPR 第 36 条）。
6. 产出 DPIA 文档，记录决策。

**踩坑点**
- 别把 DPIA 当一次性文档：处理活动变更要更新。
- 「匿名化」 vs 「假名化」：假名化后仍属个人数据，匿名化（不可逆）才不算。

## 4. 同意与隐私设计检查清单

- [ ] 同意是**自由、具体、知情、明确**的（GDPR 要求 opt-in，预勾选框无效）。
- [ ] 能「撤回同意」且和给予一样容易。
- [ ] 隐私政策写明：收集什么、为什么、保留多久、第三方是谁、用户权利如何行使。
- [ ] 默认最少收集（privacy by design / data minimization）。
- [ ] 默认关闭非必要 Cookie / 追踪（CCPA 的「Do Not Sell」入口、GDPR 的同意横幅）。
- [ ] 儿童数据：PIPL 要求 14 岁以下需监护人同意；COPPA（美国）13 岁以下。

**命令（验证同意横幅是否真拦了追踪）**
```bash
# 看站点是否在未同意前就下发了追踪 Cookie（仅做合规抽查，勿滥用）
curl -sI https://example.com | grep -iE "set-cookie"
```

## 5. 跨境传输

| 框架 | 常用机制 |
|------|---------|
| GDPR | 充分性认定国列表、**SCC（标准合同条款）**、BCR |
| PIPL | 单独同意 + **标准合同备案** / 安全评估 / 认证 |
| CCPA | 无专门跨境限制，但跨境涉及「出售/共享」需披露 |

**踩坑点**
- SCC 不是签了就完事：2020 后需做**传输影响评估（TIA）**，评估接收国法律风险。
- PIPL 标准合同需在网信办**备案**，不是内部留档即可。

## 6. 数据主体权利响应

GDPR/PIPL 共性权利：访问、更正、删除、携带、限制处理、反对。

- 设定响应时限（GDPR 1 个月可延长；PIPL 15 个工作日）。
- 身份核验后再披露，防止越权调取他人数据。
- 提供自助入口 + 人工通道。

## 7. 泄露通知时间线

- **GDPR**：发现后 **72 小时内**向监管机构报告（如对个人有高风险需同时通知用户）。
- **PIPL**：立即采取补救，通知主管部门与个人（视风险）。
- 内部：先止血（吊销凭证/隔离）+ 留存事件时间线，再走外部通知。

**踩坑点**
- 「72 小时」从**确认泄露**起算，不是从首次可疑告警起算；但拖延定性会踩雷，早报比晚报安全。
- 先通知还是先止血？先止血（控制影响），再在时限内完成法定通知。

## 8. 快速自检（上线前 5 问）

1. 我们收集的个人数据，每一项都有「合法性基础」吗？
2. 用户能方便地查看/删除自己的数据吗？
3. 跨境传了吗？机制齐了吗？
4. 日志/备份里有没有不小心落地的 PII？
5. 出事了我们能在法定时限内报吗？

> 任一项答「不确定」→ 标记为「需法务复核」，不要自行定性。本 playbook 不构成法律意见。
