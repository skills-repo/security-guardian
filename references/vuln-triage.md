# 漏洞分诊、定级与响应 Playbook

> 找到漏洞只是开始。真正决定安全水位的是：**修不修、什么时候修、谁来修、修完怎么确认**。
> 这一篇讲的是把技术发现转成组织行动的那一段。

## 1. 定级：内部排期与对外披露用两套口径

| 用途 | 用什么 | 为什么 |
|------|--------|--------|
| 内部排期 | 二维四象限（可利用性 × 影响） | 快、无歧义、直接对应"什么时候修" |
| 对外披露 / 跨团队沟通 / 合规 | CVSS v3.1 向量串 | 行业通用，可比较，有据可查 |

两套不冲突：内部用四象限决定 SLA，对外给 CVSS 分数保证口径一致。
用 `scripts/cvss_score.py` 从向量串算分，避免不同人拍脑袋给出不同分数。

```bash
python3 scripts/cvss_score.py --vector "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H"
# → 9.8 Critical
python3 scripts/cvss_score.py --interactive     # 逐项提问，适合不熟悉向量语法时
```

### CVSS 最容易填错的三项

| 指标 | 常见错误 | 正确理解 |
|------|---------|---------|
| `PR`（所需权限） | 把"需要登录"填成 `PR:N` | 需要任意登录账号 = `PR:L`；只有管理员能触发 = `PR:H` |
| `S`（作用域） | 一律填 `S:U` | 漏洞影响**越过了**受影响组件的安全边界（如容器逃逸、越权到别的租户）才是 `S:C` |
| `UI`（用户交互） | 忽略钓鱼前提 | 需要受害者点链接 = `UI:R`，会显著降低分数 |

**分数不是终点**。CVSS 9.8 的漏洞如果在一个内网只有 3 人能访问的工具上，
实际优先级可能低于一个 CVSS 6.5 但暴露在公网的越权。定级之后必须叠加**环境判断**。

## 2. 修复 SLA：写下来，否则等于没有

| 级别 | 判据 | 响应 SLA | 修复 SLA |
|------|------|---------|---------|
| **P0 紧急** | 公网可达 + 无需认证 + 可读写他人数据/提权/资金损失 | 1 小时内响应 | 24 小时内修复或下线该功能 |
| **P1 高** | 公网可达 + 需普通账号 + 高影响 | 1 个工作日 | 7 天 |
| **P2 中** | 需特殊条件 / 中等影响 | 3 个工作日 | 30 天 |
| **P3 低** | 理论风险 / 需高权限前提 / 影响有限 | 排入 backlog | 90 天或随重构 |

**P0 的关键决策是"能不能先关掉"**。修一个漏洞可能要两天，
但把该功能下线或加个功能开关只要十分钟。止血优先于修复——
这与线上事故处置的逻辑完全一致。

## 3. 一条合格的漏洞记录长什么样

写给开发看，不是写给安全团队自己看。缺任何一项都会让修复变慢：

```markdown
## [P1] 订单详情接口越权读取（IDOR）

**位置**：`src/api/orders/[id].ts:24`
**类型**：CWE-639 授权绕过 / IDOR
**CVSS**：6.5 (CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N)

**攻击场景**（谁 → 做什么 → 得到什么）
任意注册用户，把 URL 中的订单 ID 改为其他数字，即可读取他人订单，
含收货地址、手机号、商品明细。ID 为自增整数，可批量遍历，
估算可拉取全量订单数据。

**复现步骤**
1. 用账号 A 登录，访问 `/api/orders/1001`（自己的订单）→ 200
2. 保持 A 的 session，访问 `/api/orders/1002`（B 的订单）→ 200，返回 B 的数据

**根因**
查询只按 id 过滤，未附加当前用户归属条件。

**修复**（可直接粘贴）
```ts
const order = await db.order.findFirst({
  where: { id, userId: ctx.user.id }
})
if (!order) throw new NotFound()
```

**验收测试**
`test/orders.e2e.ts`：用户 A 请求 B 的 orderId，断言返回 404。

**影响范围排查**
同一模式的接口还有 `/api/invoices/[id]`、`/api/addresses/[id]`，需一并检查。
```

最后一节"影响范围排查"最常被漏——**同一类缺陷通常不止一处**。
修完单点而不做同类排查，两周后同样的问题会在另一个接口上被再次发现。

## 4. 从单点修复到根因治理

修了 5 次同类漏洞还在出现，说明修的是症状。升级路径：

```
第 1 次出现 → 修这一处
第 2 次出现 → 修这一处 + 全库 grep 同类模式，一次修完
第 3 次出现 → 加自动化门禁（lint 规则 / 单测 / CI 检查），让它无法再进主干
```

**能变成检查的，就不要靠人记住。** 举例：

| 反复出现的问题 | 治理手段 |
|---------------|---------|
| IDOR | 封装 `scopedQuery(ctx, model)` 强制带用户条件；lint 禁止裸 `findById` |
| 硬编码密钥 | CI 密钥扫描门禁（`scripts/secret_scan.py`） |
| 缺少响应头 | 网关统一注入，不由各服务自己设 |
| 依赖高危 | Dependabot 自动 PR + CI 阻断 |
| 日志打印 PII | 日志库内置脱敏中间件 |

## 5. 接收外部报告（有对外服务时必须准备）

即使不做正式的漏洞赏金，也要有一条**能被找到的联系路径**，否则研究员找不到人就会公开披露。

```
# 放在网站根目录：/.well-known/security.txt
Contact: mailto:security@example.com
Expires: 2027-01-01T00:00:00.000Z
Preferred-Languages: zh, en
Policy: https://example.com/security-policy
```

处理外部报告的基本节奏：

```
24 小时内  → 确认收到（哪怕还没验证）
7 天内     → 给出验证结论与是否受理
90 天内    → 修复完成，与报告者约定披露时间
修复后     → 致谢（如报告者愿意）
```

**最伤的做法是已读不回**。研究员等不到回应就会走公开披露，
届时你面对的是"零日 + 舆论"的双重压力。

## 6. 常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| 只给发现不给修复代码 | 开发不知道怎么改，工单挂几个月 | 每条附可粘贴的修复片段 |
| 定级只看 CVSS 不看环境 | 精力错配到低实际风险项 | CVSS 之上叠加暴露面与资产价值判断 |
| 无 SLA，全靠"尽快" | 永远排在功能需求后面 | 按级别写死 SLA 并纳入迭代计划 |
| 修完不复验 | 修得不对或被后续重构改回去 | 每条 Finding 必须有自动化验收测试 |
| 单点修复不做同类排查 | 同一缺陷在其他接口反复出现 | 每条 Finding 带"影响范围排查"一节 |
| 报告里堆低价值项 | 信噪比低，开发不再认真看 | 只交付过了三问过滤器的发现 |
| 没有对外联络渠道 | 外部研究员直接公开披露 | 部署 `security.txt` |
| 事故后不复盘 | 同类问题重复发生 | 走无指责复盘，产出治理项而非追责 |

## 7. 检查清单

**单条漏洞处理**：

- [ ] 有明确位置（文件:行号）与 CWE 分类
- [ ] 有 CVSS 向量串（用 `scripts/cvss_score.py` 算，不手填分数）
- [ ] 有攻击场景（谁 / 做什么 / 得到什么）与可复现步骤
- [ ] 有可直接粘贴的修复代码
- [ ] 有自动化验收测试
- [ ] 有同类模式的全库排查结论
- [ ] 已按级别分配 SLA 并进入排期系统（不是躺在文档里）

**流程层面**：

- [ ] 四个级别的 SLA 已书面化并被团队认可
- [ ] P0 有"先下线止血"的预案与授权路径
- [ ] 反复出现 3 次以上的问题已转为自动化门禁
- [ ] 对外服务已部署 `/.well-known/security.txt`
- [ ] 有漏洞台账，可回答"过去半年修了什么、还欠什么"
