# 威胁建模 Playbook

> 在写代码之前找出会被怎么打。威胁建模的产物不是一份文档，而是**一组必须写进代码的约束**。
>
> 参考：OWASP Threat Modeling、STRIDE、`openai/skills@security-threat-model`（4K 安装）、
> `google/mantis@mantis-threat-model`。本篇是决策方法论，不重复子技能里的操作步骤。

## 1. 什么时候值得做，什么时候是浪费

威胁建模最大的失败不是做错，是**做了一份没人看的 PPT**。先判断值不值得。

| 场景 | 做不做 | 做到什么粒度 |
|------|--------|-------------|
| 新增一个信任边界（新的外部输入源、新第三方集成） | **必须做** | 完整 DFD + STRIDE |
| 改动认证、授权、加密、支付、PII 处理 | **必须做** | 针对改动面做局部建模 |
| 新服务上线前 | 做 | 一页纸：资产 / 入口 / 最坏情况 |
| 纯 UI 改版、文案、样式 | 不做 | — |
| 内部工具、只有 3 个人能访问 | 轻量 | 只回答"如果这台机器被拿下会怎样" |
| 已经在裸奔的老系统 | **先扫描后建模** | 建模前先跑 `scripts/secret_scan.py` 和依赖审计，别在着火的房子里画图 |

**判断口诀**：这次改动有没有**改变谁能碰到什么数据**。没有 → 不用建模；有 → 必须建模。

## 2. 四问法（比 STRIDE 更适合作为入口）

按 OWASP 的四问框架推进，STRIDE 只在第二问里用：

```
Q1 我们在建什么？        → 画数据流图，标出信任边界
Q2 哪里会出问题？        → 对每条跨边界数据流套 STRIDE
Q3 我们要怎么办？        → 每个威胁给缓解措施，落到具体 issue
Q4 做得够不够好？        → 验收：缓解措施有没有对应的测试用例
```

**Q4 最常被跳过，也是最关键的一问。** 一个威胁如果没有对应的自动化测试，
下一次重构就会把缓解措施改没了，而且没人知道。

## 3. 画数据流图：只画三样东西

不要用复杂的 UML。一张图上只需要：

1. **外部实体**（谁在发起）：用户、第三方服务、定时任务、运维
2. **处理过程 + 数据存储**（谁在处理、存在哪）
3. **信任边界**（虚线）：跨过它的数据必须被当成敌意输入

```
[浏览器] --HTTPS--> ┊ --> [API 网关] --> [订单服务] --> [(订单库)]
                    ┊                        |
              信任边界①                      v
                                        ┊ --> [支付网关(第三方)]
                                   信任边界②
```

**信任边界画在哪里**——凡是满足以下任一条件的地方就有边界：

- 权限级别变化（未认证 → 已认证、普通用户 → 管理员）
- 网络区域变化（公网 → 内网、VPC 间）
- 进程 / 运行时变化（前端 → 后端、主进程 → worker、宿主 → 容器）
- 所有权变化（自有代码 → 第三方 SDK / 依赖包 / LLM 输出）

> **最容易漏掉的边界**：LLM 的输出。模型返回的内容是**不可信输入**，
> 把它直接拼进 SQL、shell、HTML 或当成权限判断依据，是 2026 年最高频的新型漏洞源。

## 4. STRIDE 逐类速查（含"这条在你系统里长什么样"）

| 类别 | 违反的属性 | 典型表现 | 优先看哪里 |
|------|-----------|---------|-----------|
| **S**poofing 伪造身份 | 认证 | JWT 未验签、可预测的 session ID、缺少 `aud`/`iss` 校验 | 登录、Token 签发与校验 |
| **T**ampering 篡改 | 完整性 | 价格/数量从前端传、隐藏字段可改、缺少 integrity hash | 表单、API 入参、CDN 资源 |
| **R**epudiation 抵赖 | 不可否认 | 关键操作无审计日志、日志可被业务账号删改 | 支付、权限变更、数据导出 |
| **I**nformation Disclosure 信息泄露 | 机密性 | 报错栈回显、目录遍历、越权读、日志打了 PII | 错误处理、文件下载、日志 |
| **D**enial of Service 拒绝服务 | 可用性 | 无限流、正则回溯（ReDoS）、无分页的查询、大文件上传 | 公开端点、搜索、上传 |
| **E**levation of Privilege 提权 | 授权 | IDOR、缺少对象级鉴权、前端隐藏按钮当权限控制 | 所有带 ID 的接口 |

**实操简化**：时间紧就只做 **S / I / E** 三类。它们覆盖了真实事故的绝大多数——
篡改和抵赖往往是这三类的后果，DoS 通常由基础设施层兜底。

## 5. 风险定级：别用五档，用二维四象限

CVSS 适合对外披露，内部排期用它太重。内部用两维打分即可：

```
              可利用性 高
                  │
   ┌──────────────┼──────────────┐
   │  ② 立刻修     │  ① 停下手上的活 │
影 │  （本迭代）   │   （今天）     │
响 ├──────────────┼──────────────┤
低 │  ④ 记进 backlog│ ③ 排期修      │  影响 高
   │              │  （本季度）    │
   └──────────────┴──────────────┘
              可利用性 低
```

- **可利用性高**：无需认证 / 无需特殊条件 / 有公开 PoC / 可远程触发
- **影响高**：可读写他人数据 / 可提权 / 可导致资金损失 / 可横向移动

对外披露或需要统一口径时，用 `scripts/cvss_score.py` 把向量串换算成分数，
避免不同人对"高危"的理解不一致。

## 6. 从威胁到代码：缓解措施必须可验收

这是威胁建模最容易空转的一步。**每条威胁产出的不是"建议加强校验"，而是三元组**：

| 威胁 | 缓解措施（具体到代码位置） | 验收方式（自动化） |
|------|--------------------------|------------------|
| 订单接口 IDOR（E） | `GET /orders/:id` 增加 `order.userId === ctx.user.id` 断言 | 集成测试：用户 A 拿 B 的 orderId 请求，断言 403 |
| 报错回显栈（I） | 全局错误中间件生产环境只返回 traceId | 单测：NODE_ENV=production 时响应体不含 `stack` |
| 登录接口爆破（S/D） | 按 IP+账号双维度限流 5 次/分钟 | 集成测试：第 6 次请求返回 429 |
| LLM 输出拼 shell（T/E） | 禁用 shell 拼接，改用参数数组 + 白名单命令 | 静态检查：禁止 `exec(` 接收变量拼接 |

**没有"验收方式"这一列的威胁模型，等于没做。**

## 7. 常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| 只对新功能建模，不看它与老功能的组合 | 漏掉链式利用（低危 + 低危 = 高危） | 至少检查新入口能到达哪些老的数据存储 |
| 把"我们用了 HTTPS/WAF"当缓解措施 | 通用防护不针对具体威胁，等于没答 | 缓解必须落到本次改动的代码或配置 |
| 建模时假设内部服务可信 | 一个服务被拿下即全线沦陷 | 服务间调用也要认证；假设内网已被渗透 |
| 威胁模型写完不更新 | 半年后与实际架构完全不符，误导后来人 | 与架构图放在同一 PR 里改，改架构必改模型 |
| 用威胁数量衡量质量 | 凑数产生一堆低价值条目 | 看有多少条产生了**代码改动或测试用例** |
| 忽略供应链与构建链 | CI 的 token 权限过大、依赖被投毒 | 把 CI/CD 也画进 DFD，它是一条真实的数据流 |

## 8. 检查清单

建模完成前逐条确认：

- [ ] 数据流图标出了**全部**信任边界，包括第三方 SDK 与 LLM 输出
- [ ] 每条跨边界数据流至少过了 S / I / E 三类
- [ ] 识别出了系统里**最有价值的资产**（钱、PII、凭据、管理权限），并单独检查其访问路径
- [ ] 每个威胁有对应缓解措施，且措施落到了具体文件/配置，不是"加强校验"
- [ ] 每个缓解措施有**自动化验收方式**，已建为 issue 或测试用例
- [ ] 高风险项（象限 ①②）已排期，不是"以后再说"
- [ ] 明确写出了**接受的风险**（哪些威胁决定不修、为什么），而不是假装它们不存在
- [ ] 模型文件与代码同仓库存放，改架构时会被一起看到
