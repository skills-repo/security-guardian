# 认证与授权 Playbook

> 认证（你是谁）和授权（你能干什么）是两件事，混在一起写就是漏洞的温床。
> 真实事故里，**授权缺陷远多于认证缺陷**——登录做得再好，一个 IDOR 就全穿了。
>
> 本篇写子技能 `skills/auth-review/` 装不下的部分：选型决策、绕过手法、以及
> 那些"看起来做了鉴权其实没做"的写法。

## 1. 认证方案选型决策树

```
用户是人还是机器？
├── 机器（服务间调用）
│   ├── 同一云内 ──────────────► 托管身份 / Workload Identity（无凭据，最优）
│   ├── CI → 云 ──────────────► OIDC 联合身份（短期令牌）
│   └── 其他 ─────────────────► mTLS 或 短期 API Token + IP 白名单
└── 人
    ├── 企业内部（已有 IdP）──► SSO（OIDC / SAML），不要自建
    ├── C 端产品
    │   ├── 想降低注册门槛 ──► 社交登录（OAuth）+ 邮箱兜底
    │   └── 需要强身份 ──────► 邮箱/手机 + 密码 + MFA
    └── 高安全场景（后台/运维）► 强制 MFA（TOTP/WebAuthn），禁用短信
```

**默认选择：用托管服务（Auth0 / Firebase Auth / Cognito / Supabase Auth / Keycloak），
不要自建。** 自建认证要正确处理密码哈希、限流、Token 生命周期、
密码重置的时序安全、账号枚举防护——每一项都有被做错的先例。

自建的唯一合理理由：有明确的合规要求禁止数据出境到该服务商，或成本在你的量级上不可接受。

## 2. Session vs JWT：不要默认选 JWT

这是最常被做错的选型。**默认应该是服务端 Session，JWT 是特殊场景的优化。**

| 维度 | 服务端 Session | JWT（无状态） |
|------|---------------|--------------|
| 立即登出 / 封禁 | ✅ 删掉即可 | ❌ 签发后无法撤销，直到过期 |
| 权限变更立即生效 | ✅ | ❌ 旧 token 里的权限仍有效 |
| 水平扩展 | 需共享存储（Redis） | ✅ 无需存储 |
| 泄露后的窗口 | 可立刻止血 | 等于 token 剩余有效期 |
| 实现复杂度 | 低 | 高（易踩签名与校验的坑） |

**决策规则**：

- 单体或少量服务 + 有 Redis → **服务端 Session**，别想太多
- 真正的多服务、跨域、需要无状态 → JWT，但**必须**配短过期（≤15 分钟）
  + Refresh Token（服务端可撤销）
- 用 JWT 又不想做 Refresh → 说明你并不需要无状态，回去用 Session

### JWT 必查的六项

```
1. alg 校验：服务端固定算法，不信任 header 里的 alg
   （防 alg:none 与 HS256/RS256 混淆攻击——把公钥当 HMAC 密钥）
2. exp 校验：必须校验，且过期时间要短
3. aud / iss 校验：防止其他系统签发的 token 被本系统接受
4. 签名密钥强度：HS256 的密钥必须是高熵随机值，不能是 "secret" 这类
5. 敏感信息不放 payload：JWT 是 base64 编码不是加密，任何人可解开看
6. 撤销机制：登出 / 改密 / 封禁时，Refresh Token 必须失效
```

## 3. 授权：三种模型与该用哪个

| 模型 | 适用 | 落地形态 |
|------|------|---------|
| **RBAC**（基于角色） | 角色数量有限、权限相对静态 | `user.role in ['admin','editor']` |
| **ABAC**（基于属性） | 需要按部门/地域/时间等维度细分 | 策略引擎（OPA / Cedar / Casbin） |
| **ReBAC**（基于关系） | 有"共享给某人""团队成员"的概念 | 关系图（SpiceDB / OpenFGA） |

**从 RBAC 起步，出现下列信号时再升级**：

- 角色数量超过 10 个，且开始出现 `admin_of_region_east` 这种组合角色 → 转 ABAC
- 出现"A 把文档共享给 B" → 转 ReBAC（RBAC 表达不了实例级共享）

### 对象级鉴权：真正的重灾区

角色鉴权（"你是 editor 吗"）和对象级鉴权（"这篇文章是你的吗"）必须都做。
**只做前者是 IDOR 的直接成因。**

```ts
// ❌ 错误：只校验了角色
async function getOrder(ctx, id) {
  requireRole(ctx, 'user')
  return db.order.findById(id)        // 任何登录用户可读任何订单
}

// ✅ 正确：把归属条件写进查询，而不是查完再判断
async function getOrder(ctx, id) {
  const order = await db.order.findFirst({
    where: { id, userId: ctx.user.id }   // 归属作为查询条件
  })
  if (!order) throw new NotFound()        // 注意：返回 404 而非 403
  return order
}
```

两个细节值得强调：

1. **把归属写进 WHERE，而不是查出来再 if 判断**。后者容易在重构中被漏掉，
   而且在批量接口里几乎必然被漏掉。
2. **无权访问返回 404 而不是 403**。403 等于告诉攻击者"这个 ID 存在"，
   是一个信息泄露面（可用于枚举）。

## 4. 常见绕过手法（审计时逐条对照）

| 手法 | 具体 | 防护 |
|------|------|------|
| 前端隐藏当权限 | 按钮不显示但接口可直接调 | 所有校验在服务端重做一遍 |
| 批量接口漏鉴权 | 单条查询有校验，`/orders?ids=1,2,3` 没有 | 批量接口的每个元素都要过同一鉴权 |
| 越权改字段 | `PATCH /users/me { role: "admin" }` | 白名单允许修改的字段，不用整体 merge |
| 越权改他人 | `PATCH /users/123`，`123` 不是自己 | 路径 ID 必须与 session 身份比对 |
| 状态机跳跃 | 直接调"发货"跳过"支付" | 状态转换校验前置状态 |
| 密码重置 token 可猜 | 用时间戳或自增作 token | 密码学随机 + 一次性 + 短过期 |
| 账号枚举 | 登录时"用户不存在"与"密码错误"提示不同 | 统一错误文案 + 统一响应时间 |
| 竞态提权 | 并发请求绕过一次性限制 | 数据库唯一约束或悲观锁，不靠应用层判断 |
| 二次验证可跳过 | MFA 页面直接跳到后续接口 | 服务端记录"已完成 MFA"的会话状态 |

## 5. 密码与凭据处理

```
哈希算法：argon2id（首选）> scrypt > bcrypt（可接受）
          ❌ 绝不：MD5、SHA-1、SHA-256（即使加盐——它们太快了）
密码策略：长度 ≥12，不强制复杂度组合，不强制定期更换（NIST SP 800-63B）
          必须做：与已泄露密码库比对（HaveIBeenPwned k-anonymity API）
限流：    按 IP + 按账号 双维度，失败后指数退避
存储：    只存哈希；重置流程不能回显原密码（能回显 = 明文存储）
```

> **不要强制 90 天改密码**。NIST 已明确反对——它导致用户使用 `Password1!`、
> `Password2!` 这类可预测变体，反而降低安全性。

## 6. 常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| 认证与授权写在同一个中间件里 | 改一个动到另一个，容易出现"登录即放行" | 两层分开：先认证，再按资源授权 |
| 在网关做完鉴权，服务内不再校验 | 网关被绕过或内网可直连时全线失守 | 服务内独立校验（零信任） |
| Cookie 缺 `HttpOnly` / `Secure` / `SameSite` | XSS 可直接偷走会话 | 三个属性都设；见 `references/web-hardening.md` |
| 登出只清前端存储 | 服务端 session/token 仍有效 | 服务端显式失效 |
| 用邮箱做主键 | 用户改邮箱后关联数据错乱；邮箱可被回收 | 用不可变内部 ID 做主键 |
| OAuth 回调不校验 `state` | CSRF 绑定攻击 | `state` 必须随机且校验 |
| OAuth 重定向 URI 用通配符 | 授权码被劫持到攻击者域名 | 精确匹配，不用通配 |
| 权限判断依赖 LLM 输出 | 提示注入即提权 | 权限判断必须是确定性代码 |

## 7. 检查清单

**认证**：

- [ ] 密码用 argon2id / scrypt / bcrypt 哈希
- [ ] 登录接口按 IP + 账号双维度限流
- [ ] 错误提示不区分"用户不存在"与"密码错误"
- [ ] 使用 JWT 时：固定 alg、校验 exp/aud/iss、短过期 + 可撤销的 Refresh Token
- [ ] 登出 / 改密 / 封禁能让既有会话立即失效
- [ ] 后台与运维入口强制 MFA（优先 WebAuthn / TOTP，不用短信）
- [ ] OAuth 流程校验 `state`，重定向 URI 精确匹配

**授权**：

- [ ] 每个带资源 ID 的接口都做了对象级鉴权，且归属写在查询条件里
- [ ] 批量接口对每个元素独立鉴权
- [ ] 可更新字段走白名单，不整体 merge 请求体
- [ ] 无权访问返回 404 而非 403（防枚举）
- [ ] 服务间调用有独立认证，不假设内网可信
- [ ] 状态机转换校验前置状态
- [ ] 权限变更后旧凭据不再具备旧权限

**Cookie / 会话**：

- [ ] `HttpOnly` + `Secure` + `SameSite=Lax|Strict`
- [ ] Session ID 密码学随机、登录后重新生成（防固定攻击）
- [ ] 有空闲超时与绝对超时
